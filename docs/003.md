# Audit: USB Wireless Mouse Undetected After Login (Needs Unplug–Replug)

**Date:** 2026-10-26
**Host:** HP EliteBook (AMD Renoir/Cezanne), Debian GNU/Linux 13 (trixie), kernel 6.12.113+deb13-amd64, XFCE + LightDM
**Audit constraints:** performed non-root (per AGENTS.md). Commands requiring root are listed as proposals and were **not** executed.

## Issue Summary

After every login, the USB wireless mouse is dead (no cursor movement) even though the system is fully up.
The only way to revive it is to physically unplug and re-plug the USB receiver dongle.
The problem reproduces on every boot; after one replug the mouse works indefinitely.

## Hardware Identification

* **Receiver (USB dongle):** `Maxxter Wireless Receiver` — actually a **Telink**-based 2.4 GHz receiver
  * USB ID: `248a:8514` (vendor "Maxxter", product "Wireless Receiver", manufacturer string "Telink")
  * USB 1.10 Full Speed, `bMaxPower = 50 mA`, `bmAttributes = 0xa0` (bus-powered, remote-wakeup capable)
  * Two HID interfaces: `3-2:1.0` (boot mouse) and `3-2:1.1` (consumer/system control), both bound to `usbhid`
  * Connected to Bus 3 Port 2: `/sys/bus/usb/devices/3-2` (`pci-0000:03:00.4-usb-0:2`)
* **USB controller:** AMD Renoir/Cezanne USB 3.1 xHCI `[1022:1639]` (`03:00.4`)
* **Mouse:** Maxxter 2.4 GHz wireless mouse, paired to the dongle (plug-and-play, no dedicated pairing observed)

## Root-Cause Analysis

### Ruled out (with evidence)

1. **USB autosuspend / power management** — device `control=on`, not whitelisted; problem occurs immediately after boot, not after idle.
2. **Missing or misbehaving driver** — `usbhid` binds both interfaces; X/libinput attach works every enumeration.
3. **udev/modprobe misconfiguration** — no custom rules or quirks touch this device.
4. **xfce4-power-manager / DPMS** — settings only blank the display; suspend is 60 min idle; machine is on AC ("Charging").
5. **X/libinput race** — X attach/remove events mirror physical replugs 1:1; no ghost events.
6. **Insufficient port power** — dongle draws 50 mA max.

### Most probable root cause (firmware-level, confidence: high for the layer, medium for exact mechanism)

The Telink receiver enumerates cleanly over USB at cold power-on, but its **RF link to the mouse never comes up** (pairing/handshake window missed or firmware boot race). Unplugging drops VBUS → hard firmware reset → on re-insertion the RF link re-establishes.

Two mechanisms fit, and the discriminating test is cheap (see checklist):

* **A. Dongle-side:** its firmware only (re)initializes the RF stack on a clean USB power-on/reset, and the boot-time port reset sequence (AMD xHCI cold port power-up) leaves it half-initialized.
* **B. Mouse-side:** the mouse was in deep sleep at dongle boot; the dongle's pairing window expired before the mouse woke, and it never retries.

Either way this is a **device firmware limitation**, not a Debian configuration bug. The class of symptom ("enumerates fine, dead until replug") is typical of low-cost 2.4 GHz receivers.

### Evidence gap (needs root — pending approval)

Kernel messages for the boot window would confirm there is no hidden USB-level error (e.g. descriptor retries) and would capture the dongle's power-on sequence:

```sh
sudo journalctl -k -b 0 --no-pager | grep -iE 'usb|xhci|hid|248a|8514|3-2'
```

Optional, to enable future non-root kernel log reads:

```sh
sudo usermod -aG systemd-journal,adm anoop
```

(re-login required afterwards)

## Recommended Fixes (all require approval — none executed)

### 1. Diagnostic: confirm the layer before fixing

At next boot, when the mouse is dead, **do not replug immediately**:

1. Toggle the mouse power switch OFF→ON, then move/click it.
   * If it revives → mouse-side handshake (mechanism B); fix = wake order (turn mouse on after the dongle LED settles), or replace dongle with a better one.
   * If still dead → dongle-side (mechanism A); continue to fix #2.
2. Try a **software replug** instead of physical replug:

```sh
DEV=/sys/bus/usb/devices/3-2
sudo sh -c "echo 0 > $DEV/authorized && sleep 1 && echo 1 > $DEV/authorized"
```

If this revives the mouse, physical replugging is never needed again — the rest is just automation.

### 2. Automate the software replug at login (workaround)

A systemd oneshot that runs after the display manager starts, matching the dongle by VID:PID so it survives port changes:

```sh
# /usr/local/sbin/usb-mouse-replug.sh
#!/bin/sh
for d in /sys/bus/usb/devices/*/idVendor; do
    dir=$(dirname "$d")
    if [ "$(cat "$dir/idVendor")" = "248a" ] && [ "$(cat "$dir/idProduct")" = "8514" ]; then
        echo 0 > "$dir/authorized"
        sleep 1
        echo 1 > "$dir/authorized"
    fi
done
```

```ini
# /etc/systemd/system/usb-mouse-replug.service
[Unit]
Description=Power-cycle Maxxter/Telink wireless mouse receiver after boot
After=display-manager.service
Wants=display-manager.service

[Service]
Type=oneshot
ExecStart=/usr/local/sbin/usb-mouse-replug.sh

[Install]
WantedBy=multi-user.target
```

Enable with: `sudo systemctl enable --now usb-mouse-replug.service` (the `--now` run may be skipped for the first test).

### 3. Hardware-level options (no software change)

* Move the dongle to a different USB port (different xHCI controller: `03:00.3` also exists) — cold-boot port behavior differs per controller.
* Disable the mouse's deep-sleep before boot (some mice have a channel switch — changing channel forces a re-pair).
* If a firmware/pairing utility exists for Telink receivers (Windows-only in practice), re-pair on another machine.
* Long term: a receiver from a vendor with Linux-friendly firmware (e.g. Logitech Unifying) avoids this class of issue entirely.

## Next-Boot Verification Checklist

1. Boot, log in, confirm mouse dead.
2. Run test from Fix 1 (mouse power toggle → software replug) and note which one revives it.
3. Run the root journalctl command above and check for `248a:8514`-related lines around the 08:56-style boot window (look for `device descriptor read` retries, `reset` loops, or silence = clean enumeration).
4. If Fix 2 is approved and installed, verify the mouse works right after login with no manual action.

## Conclusion

The OS stack (xHCI → usbhid → udev → libinput/X) is healthy and provably attaches the receiver at boot; the failure is in the **receiver firmware's 2.4 GHz link initialization at cold power-on**. Unplug-replug works because it power-cycles the dongle. The cleanest software remedy is an authorized-toggle ("software replug") automated at login, pending the discriminating test and your approval.

## Addendum (2026-10-27): Suspend/Resume Revives the Mouse Without Replug — New Evidence

### Observation (user report)
After trying a sleep cycle (user unsure whether suspend or hibernate), the mouse worked **without** any replug.

### What the evidence shows (non-root, same boot as the audit)

1. **It was suspend (s2idle), not hibernate, and not a reboot.**
   * `who -b` unchanged (2026-10-26 08:56); `boot_id` identical to yesterday.
   * Wall-clock-since-boot == `/proc/uptime` exactly (1548 min both) → no power-off gap → RAM stayed powered → hibernate ruled out (hibernate resume would show a new boot).
   * `/sys/power/mem_sleep` = `[s2idle]` → this machine's "suspend" is suspend-to-idle; deep S3 not available.
2. **The sleep cycle is visible in the logs.** One cycle this morning ~08:04:10 → 08:07:26 (~3 min): user-session `bluetooth.target` stop/restart at 08:07:26 + X server final VT-switch pair (`Xorg.0.log` [54919.769] suspend → [55115.255] resume) followed by the standard post-resume re-probe of all input devices. Several earlier VT-switch pairs exist across the 26 Oct evening/night (13:14→13:49, 17:36→18:15, 21:03→21:31, 22:28→22:35, 22:59→23:13, 00:32→00:35).
3. **The dongle was NOT re-enumerated by the sleep cycle** — the OS kept the exact same USB session:
   * `devnum` still 5; HID instances still `.0006/.0007` (created by the 10:14:45 replug on 26 Oct)
   * `USEC_INITIALIZED` unchanged; no new `config/udev: Adding ... Telink` entries in the X log after `[4709]`
   * `power/runtime_suspended_time = 0`, `control=on`, `runtime_status=active`

### Interpretation

Whatever revived the mouse happened **at the device level**, invisible to the USB/HID stack:

* During system suspend the kernel takes **every** USB device and the xHCI host through a suspend→resume cycle — `power/control=on` only disables *runtime* autosuspend, not system sleep. The Telink dongle's MCU therefore goes through a device-level suspend/resume (reset) path, which its firmware evidently treats as a **re-initialization trigger for the 2.4 GHz link**. That is the same "kick" as the physical replug, applied electrically in place.
* `persist=1` is why the same enumeration survives across the cycle: no re-plug signature anywhere in the logs (same devnum, same HID instances, no udev re-adds).
* Complementary possibility: the *mouse* side may simply re-sync its RF link after the dongle goes quiet during sleep. The mouse power-toggle test (below) discriminates this.

### Updated discriminating test for next boot (mouse dead after login)

Try in this order and note which one revives it:

1. **Mouse power switch OFF→ON only** (no USB action) → if this revives it, the resync happens mouse-side; fix = wake order (switch mouse on after dongle settles).
2. **Suspend + resume** (`systemctl suspend`, then wake) → if this revives it, the dongle firmware re-inits its radio on USB resume; suspend is a usable manual workaround, but the authorized-toggle remains faster and works without sleeping.
3. **Authorized toggle** (`echo 0 > /sys/bus/usb/devices/3-2/authorized; sleep 1; echo 1 > .../authorized`) → if this revives it, a pure device reset suffices → automate via the proposed `usb-mouse-replug.service`.

### Consequence for the workaround ranking

This finding **confirms the root cause** in the main report: the dongle only needs *some* form of device-level reset kick after cold power-on (VBUS drop, USB suspend/resume, or authorized toggle). It also gives a second, independent "revive" path that requires no hardware action at all. The `usb-mouse-replug.service` login workaround remains the recommended permanent fix.
